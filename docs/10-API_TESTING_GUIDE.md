# 10 - API Testing Guide (end to end)

> **Generated by `npm run docs:guide`** from a real run of the API (2026-11-03). Do not edit by hand: change the code, then re-run it. It fails if any step returns an unexpected status, so it is also a smoke test.

This guide shows the whole life of the API: the operator creates a company, its first Admin signs in, manage employees, invite people, refresh tokens, deactivate, and prove that companies cannot see each other. Every step shows the request body and the real response.

## 1. Set up (5 minutes)

```bash
docker compose up -d postgres          # PostgreSQL (on a machine with a native PostgreSQL, map the port to 5433)
cd apps/api
npx prisma migrate deploy && npx prisma db seed
npm run start                          # API on http://localhost:4000/api
```

| What | Where |
|---|---|
| Interactive docs (try routes in the browser) | http://localhost:4000/api/docs |
| OpenAPI file for Apidog / Postman | http://localhost:4000/api/docs-json  or  `docs/api/openapi.json` |
| Development Admin (from the seed) | `admin@checkpoint.local` / `AdminPassword123!` |

**Test with:** Swagger UI (click **Authorize**, paste the `accessToken`), Apidog, Postman, or `curl`.

## 2. Six ideas you need

1. **Two tokens.** Login returns an `accessToken` (15 minutes, send it as `Authorization: Bearer ...`) and a `refreshToken` (30 days, single-use, exchanged at `/auth/refresh`).
2. **Roles.** `ADMIN` may call `/admin/*`. `EMPLOYEE` gets **403** there and may call `/me/*`. An account that still has a one-time password gets **403 `PASSWORD_CHANGE_REQUIRED`** everywhere until it calls `PATCH /me/password`.
3. **Company scope.** Your company is inside your token. You never send it. Another company's record answers **404**, exactly like a missing one.
4. **Two ways to carry the token.** Mobile and tools use `Authorization: Bearer`. Web apps use HttpOnly cookies (header `X-Auth-Mode: cookie`, see Part H) and send `X-CSRF-Token` on writes. The header wins if both are present.
5. **Errors** always look like `{ "statusCode": 404, "message": "...", "error": "Not Found" }`. A 400 lists every validation problem and rejects unknown fields.
6. **Money** is EGP, and amounts come back as strings (`"12000"`).

## 3. The cycle, step by step

Everything below was produced by really calling the API (values such as ids and dates differ on your machine). Tokens are shortened.

### Part 0: Create a company and its first Admin (operator, no HTTP route)

Only the platform operator can do this, from the server, with the database credentials. There is no API route for it. Full procedure: `docs/11-PROVISIONING_RUNBOOK.md`. In these steps the secret is the value of `PROVISIONING_SECRET` (16+ characters) and is never printed.

### Step 1. A wrong secret creates nothing

The command checks the secret before it touches the database.

**Command** (run by the operator, in `apps/api`)

```bash
npm run -s provision:company -- --secret "not-the-secret-0000" --name "Acme 1793718338317" --slug acme-1793718338317 --admin-email owner-1793718338317@acme.test
```

**Output** (exit code 1)

```text
❌ Wrong or missing --secret. Nothing was created.
```

### Step 2. Create the company and its first Admin

One transaction creates the company, its default settings and shift, the Admin user with the ADMIN role, and sets the company owner. A random one-time password is printed once. Give it to the Admin privately.

**Command** (run by the operator, in `apps/api`)


### Part D: Tokens, refresh and theft detection

### Step 42. Refresh

Returns a NEW pair. The refresh token you sent is now spent: replace both stored tokens.

**Request**

```http
POST /api/auth/refresh
Content-Type: application/json

{
  "refreshToken": "64606cabacbe49ac51…(64 chars)"
}
```

**Response 200**

```json
{
  "accessToken": "eyJhbGciOiJIUzI1Ni…(516 chars)",
  "refreshToken": "88d286d65a93b13e1d…(64 chars)"
}
```

### Step 43. Replay the spent refresh token (a stolen copy)

Reuse is treated as theft: the whole session family is revoked and this returns 401.

**Request**

```http
POST /api/auth/refresh
Content-Type: application/json

{
  "refreshToken": "64606cabacbe49ac51…(64 chars)"
}
```

**Response 401**

```json
{
  "message": "Refresh token reuse detected. All sessions in this family revoked.",
  "error": "Unauthorized",
  "statusCode": 401
}
```

### Step 44. The legitimate newer token is dead too

Because the family was revoked, the user must sign in again. This is the intended safety behaviour.

**Request**

```http
POST /api/auth/refresh
Content-Type: application/json

{
  "refreshToken": "88d286d65a93b13e1d…(64 chars)"
}
```

**Response 401**

```json
{
  "message": "Refresh token reuse detected. All sessions in this family revoked.",
  "error": "Unauthorized",
  "statusCode": 401
}
```

### Part H: Web clients (cookie mode)

A browser app (Next.js) keeps the tokens in HttpOnly cookies, so page JavaScript can never read them. It asks for this with the header `X-Auth-Mode: cookie`. Everything else is the same API. Mobile apps and tools keep using the bearer header, as in Parts A to G. If a request carries both, the header wins. In production the cookies are also `Secure`, and browsers may call the API only from the origins in `CORS_ORIGINS`.

### Step 60. Sign in in cookie mode

The tokens arrive as `Set-Cookie` (HttpOnly, SameSite=Lax) and are NOT in the body. The body holds the user and a `csrfToken`. Keep the `csrfToken` in memory.

**Request**

```http
POST /api/auth/login
X-Auth-Mode: cookie
Content-Type: application/json

{
  "email": "admin@checkpoint.local",
  "password": "AdminPassword123!"
}
```

**Response 200**

```http
cp_access=eyJhbGciOiJI…; Max-Age=900; Path=/api; Expires=Tue, 03 Nov 2026 15:21:01 GMT; HttpOnly; SameSite=Lax
cp_refresh=85fb6c87a6eb…; Max-Age=2592000; Path=/api/auth; Expires=Thu, 03 Dec 2026 15:06:01 GMT; HttpOnly; SameSite=Lax
```

```json
{
  "user": {
    "id": "c0e80d90-016c-47a4-80f9-5140c19a180e",
    "email": "admin@checkpoint.local",
    "fullName": "System Administrator",
    "role": "ADMIN",
```

### Step 65. Sign out in cookie mode

Revokes the whole session family and clears both cookies (`Max-Age=0` / expired).

**Request**

```http
POST /api/auth/logout
X-Auth-Mode: cookie
Cookie: cp_refresh=a5b69e673dab…
```

**Response 200**

```http
cp_access=; Path=/api; Expires=Thu, 01 Jan …; HttpOnly; SameSite=Lax
cp_refresh=; Path=/api/auth; Expires=Thu, 01 Jan …; HttpOnly; SameSite=Lax
```

```json
{
  "success": true,
  "message": "Logged out successfully"
}
```

### Step 66. The refresh cookie no longer works

After sign-out the old refresh token is revoked: **401**.

**Request**

```http
POST /api/auth/refresh
X-Auth-Mode: cookie
Cookie: cp_refresh=a5b69e673dab…
```

**Response 401**

```http
cp_access=; Path=/api; Expires=Thu, 01 Jan …; HttpOnly; SameSite=Lax
cp_refresh=; Path=/api/auth; Expires=Thu, 01 Jan …; HttpOnly; SameSite=Lax
```

```json
{
  "message": "Refresh token reuse detected. All sessions in this family revoked.",
  "error": "Unauthorized",
  "statusCode": 401
}
```

## 5. Status codes you will meet

| Code | Meaning here |
|---|---|
| 200 / 201 | Done |
| 400 | Invalid body, or an invalid/used/expired invitation token |
| 401 | No/expired token, wrong credentials, deactivated account, or a refresh token that is spent |
| 403 | Signed in, but your role lacks the permission |
| 404 | Not in **your** company (or does not exist) |
| 409 | Duplicate (email, employee code, pending invitation) or wrong state |
| 429 | Too many WRONG login, invitation or password attempts (successful sign-ins never count) |

## 6. Import into Apidog (or Postman / Insomnia)

1. Start the API, or just use the file `docs/api/openapi.json`.
2. **Apidog:** *Project settings → Import data → OpenAPI/Swagger →* choose the file, **or** paste the URL `http://localhost:4000/api/docs-json` (re-import it any time to refresh).
3. Create an environment variable `baseUrl = http://localhost:4000` and a variable `accessToken`. Set the project's auth to *Bearer Token* = `{{accessToken}}`.
4. Run **POST /api/auth/login**, copy `accessToken` into the variable, then run any route.
5. The request bodies already contain working examples; the schemas list every field with its type and example.

## 7. Keeping the docs current (for developers)

- Every route needs `@ApiOperation` (with a scenario), `@ApiTags`, and response decorators. Request and response bodies are classes with `@ApiProperty`.
- After adding or changing a route run **`npm run docs:openapi`** (rewrites `docs/api/openapi.json`) and **`npm run docs:guide`** (rewrites this file).
- The unit test `src/swagger.spec.ts` **fails** if `docs/api/openapi.json` is out of date or a route has no summary, tag or response, so CI catches a forgotten update.
